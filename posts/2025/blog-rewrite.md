## 为什么离开 xLog

近两年，我一直在 [xLog](https://xlog.app) 上写博客。xLog 是一个基于区块链的去中心化博客平台，理念很美好，但随着时间推移，它逐渐不再适合我了。

**首先，xLog 已经停止开发。** 作为开发者，我深知一个不再维护的平台意味着什么——没有新功能、没有 bug 修复、没有性能优化。更重要的是，Web 技术发展很快，一个不再迭代的平台会逐渐落后于时代。

**其次，平台上充斥着低质量内容。** 去中心化的理念固然美好，但缺乏内容审核机制导致内容质量参差不齐。我希望博客是一个纯粹的技术分享和生活记录空间，而不是被比特币、区块链的营销号和低质量内容包围。

**最后，也是最重要的——我需要更多定制化功能。** 生活发生了一些变化，我发展了一段恋爱关系。这带来了新的需求：我想要一个专属的发言小空间，一个可以承载生活温度的地方。xLog 的功能相对固定，无法满足这些个性化需求。

比如，我想要一个「碎碎念」功能，记录每天的小想法、小确幸，通过暴露 API，支持文本和图片的快速发布和分享。这些功能在现成的平台上都难以直接实现。

## 为什么选择自己开发

离开 xLog 后，我开始考虑下一步该怎么办。摆在面前的选择有很多：

**现成的博客平台**：[WordPress](https://wordpress.org)、[Ghost](https://ghost.org)、[Hexo](https://hexo.io)、[Hugo](https://gohugo.io) 等成熟的博客系统，开箱即用，功能完善。但依然是"框架内"的自由，定制化程度有限。

**文档框架**：[VitePress](https://vitepress.dev)、[Docusaurus](https://docusaurus.io) 等静态站点生成器。它们的定制性更强，但主要面向文档场景，博客功能需要自己扩展。

**技术社区平台**：[掘金](https://juejin.cn)、[知乎](https://zhihu.com)、[Medium](https://medium.com) 等内容平台，流量大，传播快。但内容不归自己掌控，平台规则随时可能变化。

**GitHub Issues**：简单直接，完全基于 Git，有人用它当博客。但功能太基础，体验也受限于 GitHub 的界面和互联网状态。

**从零开发**：完全的掌控权和自由度，但需要投入更多时间和精力，需要自己解决所有问题。

经过权衡，我最终选择了使用 [Next.js](https://nextjs.org) 从零开发。

### 混合渲染：静态与动态的平衡

选择 Next.js 不是因为它流行，而是因为它的 [App Router](https://nextjs.org/docs/app) 让我可以同时拥有静态和动态的优势。

在做技术选型时，我首先考虑的是系统的核心需求：博客需要极致的访问速度，但也要支持便捷的内容更新。文章列表和详情页通过静态生成（SSG），构建时就生成好了 HTML，访问速度极快。同时，我又能写 API Routes 来动态更新内容——比如通过 Next.js 的动态 API 端点更新碎碎念内容。

这里有个有趣的设计：当通过 API 添加新内容后，系统会自动向 [GitHub](https://github.com) 仓库提交更新。GitHub 收到新提交后触发 [Webhook](https://docs.github.com/webhooks)，[Vercel](https://vercel.com) 会自动重新构建整个站点，大约 1 分钟后新内容就能在页面上显示。这是静态生成的特性，不是缺陷。相比完全动态的方案，这种方式让页面访问速度极快（通常不到 100 毫秒），而一两分钟的更新延迟对于博客这种非实时场景完全可以接受。

为了让内容发布更便捷，我还集成了 QQ 机器人。只需要在 QQ 上发送消息，机器人就会自动调用 API 添加内容——这意味着可以随时随地用手机发布碎碎念和 Mio 说，不需要打开电脑，不需要编辑器，甚至不需要懂技术。这种方式把发布门槛降到了最低，让记录变得像发微信一样简单。

这种混合模式在传统博客平台很难实现。要么完全静态，更新需要重新构建；要么完全动态，性能受影响。而 Next.js 让我鱼和熊掌兼得。

[React 19](https://react.dev/blog/2024/12/05/react-19) 的编译器自动优化了组件的重渲染，省去了很多性能优化的麻烦。[Tailwind CSS v4](https://tailwindcss.com/blog/tailwindcss-v4-alpha) 采用了新的 CSS-first 配置方式，直接在样式文件中定义主题变量，不再需要传统的配置文件。博客使用了 [OKLCH 色彩空间](https://oklch.com) 来定义所有颜色，这是一种感知均匀的色彩模型，比传统的 RGB 或 HSL 更科学——相同的明度数值在视觉上真的是相同的亮度，这让颜色调整变得更加直观可控。

### AI 辅助开发的真实体验

AI 辅助开发确实帮了大忙。这个博客从零到上线大约用了 3-4 天：

第一天主要做架构设计和核心功能，AI 帮我搭建基础结构、实现文章的静态生成、设计色彩系统。第二天实现特殊功能，包括碎碎念和 Mio 说的数据结构、API Routes 和 GitHub 集成。第三天是细节优化，反复调整 Mio 说的粉色配色（尝试了很多个色值）、实现主题切换和响应式设计。第四天测试和部署，添加各种小功能，配置 SEO 和站点地图。

AI 主要帮助生成重复性的样板内容、调试技术问题、优化细节。但关键决策——比如选择什么技术栈、如何设计架构、UI 细节要求和产品理念——都是我自己做的。AI 是效率工具，不是替代思考的工具。比如这篇文章，就是我和 [Claude Code](https://claude.com/claude-code) 一起完成的——我提供想法、基础内容、行文框架和技术判断，Claude 帮我整理和润色表达。

### 成本与性能

托管在 Vercel，运行成本几乎为零。Vercel 的 Hobby 免费套餐提供每月 100GB 的带宽，而个人博客的流量通常只有 1-2GB，完全够用。它的全球边缘网络让访问速度很快，还会自动优化图片和资源。唯一的成本是域名费用，一年大约一百块钱。

性能表现上，静态页面的首次内容渲染通常在 1 秒内，最大内容绘制在 1.5 秒内，[Lighthouse](https://developer.chrome.com/docs/lighthouse) 的性能评分在 95 分以上。这些数字的背后是静态生成带来的优势——页面在构建时就已经生成好了，访问时直接返回 HTML，不需要服务器端渲染或数据库查询。

### 完全掌控

最重要的是，**我拥有对博客的完全掌控权**。可以根据需求随时调整技术方案，可以尝试新的技术实践，可以优化任何想优化的地方。

所有代码都在我的 GitHub 仓库中，可以随时查看、修改、备份。这种掌控感，是任何第三方平台都无法提供的。

当然，自己开发也需要投入时间和精力。但对我来说，这个过程本身就是一种技术实践和能力提升，值得投入。

## 设计理念：简约中的温度

在设计这个博客时，我一直在思考一个问题：如何让一个技术博客既保持专业简洁，又能承载生活的温度？

### 极简主义：黑白灰的纯粹

博客的主体设计非常极简——只使用黑、白、灰三种颜色。没有花哨的动画，没有复杂的交互，只有纯粹的文字和内容。

这种极简设计不是偷懒，而是一种克制。见过太多为了炫技而堆砌功能的项目，最终都因为过度复杂而难以维护。好的设计应该是做减法，只保留最核心、最必要的元素。

我希望读者的注意力能集中在内容本身，而不是被花哨的设计分散。但极简不等于冷漠。在保持整体简洁的同时，我为生活化的内容添加了一些色彩。

### 黑白灰与粉色：理性与温馨

这是整个设计中我最喜欢的部分。

博客的主体和「碎碎念」都保持黑白灰的极简设计——这代表着理性和专业，无论是技术文章还是日常记录，都统一在这种克制的色调中。

唯一的例外是「Mio 说」。这个板块使用粉色作为点缀——不是因为 Mio 喜欢粉色，而是因为粉色代表着温馨和柔软。当我在设计这个板块时，我一直在想：什么样的颜色才能代表这个空间的氛围？最后选择的是一种温柔但不失存在感的粉色——在亮色模式下是温暖的粉，在暗色模式下是柔和的粉。这个选择经过了多次调整和对比，直到找到那个「刚刚好」的色调。

碎碎念其实也考虑过使用蓝色点缀，代表理性和思考。但最终选择保持黑白灰的极简设计，让 Mio 说的粉色成为整个博客中唯一的色彩点缀。这种设计更具辨识度，也让那个空间更显专属和特别。

这种设计不仅仅是视觉上的区分，更是一种氛围的营造：

- 博客主体和碎碎念的黑白灰，代表着理性和专业
- Mio 说的粉色点缀，代表着温馨和专属

当你打开「Mio 说」页面，页面中的标题、线条等元素使用粉色点缀。那一刻，你会感觉到这个空间的氛围不一样——温馨、柔软、专属。

### 阅读体验：让文字呼吸

文章的宽度、行高、字间距，都经过仔细调整。合适的行宽（65-75 个字符）、舒适的行高（1.6-1.8）、恰当的字间距——这些数字背后是科学研究和用户体验的最佳实践。

移动端的体验也很重要。响应式设计不是简单的媒体查询，而是针对不同设备特性做针对性优化。小屏幕上字体会稍微大一点，交互区域会更大，导航会更简洁。移动设备是很多人的主要阅读场景，体验必须做好。

### 一些小心思

有些优化可能不容易被注意到，但它们确实存在：

**视觉细节**：
- 所有外链都会自动添加 ↗ 图标，提示这是一个外部链接
- 链接使用虚线下划线，鼠标悬停时切换为实线
- 主题切换时没有闪烁，过渡非常平滑（使用 [CSS 过渡动画](https://developer.mozilla.org/docs/Web/CSS/transition)）
- 超过一年的旧文章会自动显示提示横幅，告知读者内容可能过时

**内容体验**：
- 每篇文章都会自动计算阅读时间（按平均阅读速度计算）
- 代码块使用 [Shiki](https://shiki.style) 实现精确的语法高亮，支持多种主题
- 图片自动优化为 [WebP](https://developers.google.com/speed/webp) 格式，并根据设备屏幕尺寸响应式加载
- 支持 [PWA](https://web.dev/progressive-web-apps)，可以"添加到主屏幕"，像原生应用一样使用

**文本处理**：
- 自动为中英文混排添加空格（[盘古之白](https://github.com/vinta/pangu.js)），让排版更舒适
- 自动规范化专有名词的大小写（比如 React、Next.js、TypeScript）
- 保护 [Markdown](https://www.markdownguide.org) 语法不被格式化破坏，支持加粗、链接等格式

**SEO 优化**：
- 自动生成站点地图（[Sitemap](https://www.sitemaps.org)）和 [Robots.txt](https://developers.google.com/search/docs/crawling-indexing/robots/intro)
- 动态生成 [RSS](https://www.rssboard.org/rss-specification) 订阅源，方便 RSS 阅读器订阅
- 每篇文章自动生成 [Open Graph](https://ogp.me) 图片，社交媒体分享时有精美预览

这些小心思可能不会被所有人注意到，但我知道它们在那里。就像生活中的很多小事，不需要被看见，但它们让一切变得更好。

## 特殊的功能设计

### 碎碎念：记录生活的点滴

「碎碎念」是我为自己设计的功能。它不是传统的博客文章，而是类似 Twitter 的短内容——记录生活中的点滴想法、小确幸、突然的灵感。

有时候是一句话，有时候是一段观察，有时候只是一个感叹。这些内容不需要长篇大论，不需要完整的逻辑，只需要记录下那一刻的感受。

技术实现上，碎碎念的内容存储在 [JSON](https://www.json.org) 文件中，每条记录包含 ID、时间戳和内容。通过 API 接口可以远程添加新内容，系统会自动提交到 GitHub 仓库并触发重新构建。

为了让发布更便捷，我集成了 QQ 机器人——直接在 QQ 上发消息就能添加碎碎念，不需要打开电脑或编辑器。支持小时级别的更新，意味着我可以随时记录——早上起床时的想法，中午吃饭时的观察，晚上睡前的感慨，都会被保留在这里。每条内容还支持添加图片，通过图床存储图片链接。机器人会自动调用 API，几分钟后内容就会出现在博客上。

### Mio 说：粉色点缀的专属空间

「Mio 说」是这个博客中比较特别的功能。

这个板块使用粉色作为视觉点缀，标题、线条等关键元素采用粉色，在黑白灰的基调上营造出一种温暖的氛围。这种克制的用色方式，既保持了整体的简洁，又让这个板块有了独特的辨识度。

技术实现上，Mio 说的架构和碎碎念类似——独立的 JSON 数据文件、独立的 API 端点、独立的页面展示。虽然底层使用相同的 API 鉴权机制，但通过 API 端点分离和数据文件分离，实现了内容的逻辑独立。这是一种通过技术架构和约定构建的"专属空间"——内容会被完整地保留在独立的数据文件中，通过 [Git](https://git-scm.com) 版本控制记录每一次更新。

Mio 说同样集成了 QQ 机器人，可以直接在 QQ 上发送内容。这个设计的初衷是想打造一个独立的记录空间，让内容能够被完整地保留，同时降低发布门槛——不需要懂技术，不需要打开电脑，随时随地都能记录。Mio 说也支持图片和 Markdown 格式（比如加粗文字），让表达更丰富。

### 大事记：时间线上的记录

大事记记录生活中重要的时刻和里程碑。

每条记录都包含日期和描述，按时间线排列。这不是流水账，而是那些值得被记住的瞬间。技术实现上同样使用 JSON 文件存储，保持了整个博客数据管理的一致性——所有内容都是纯文本文件，用 Git 管理版本，可以随时查看每一次修改的历史。

时间会流逝，记忆会模糊，但这些记录会一直在这里。多年以后翻看这些大事记，能想起那些时刻的感受和心情。

## 设计中的取舍

在开发过程中，我做了很多选择和取舍。

### 为什么不用数据库

最初我考虑过使用数据库来存储内容，但最终选择了更简单的方案——用文件存储。

这个决策看似简单，实际上是经过深思熟虑的。在做架构设计时，我会先评估项目的实际需求和规模，而不是盲目追求技术的完整性。数据库固然强大，但它带来的复杂度和维护成本，对于这个博客来说是不必要的。过度设计的危害很明显——不是每个项目都需要微服务，不是每个应用都需要数据库。

文件存储的好处是：

**简单可靠**：所有内容都是纯文本文件（[Markdown](https://www.markdownguide.org) 和 [JSON](https://www.json.org)），可以用任何编辑器打开和编辑。不需要运行数据库服务器，不需要担心数据库连接、备份、迁移等问题。

**版本控制**：用 [Git](https://git-scm.com) 管理所有内容，每一次修改都有完整的历史记录。可以随时回滚到任何历史版本，可以看到内容是如何演变的。这种透明度是数据库难以提供的。

**数据自由**：内容完全属于自己，不被任何格式锁定。想迁移到其他平台？直接复制文件就行。想备份？Git 仓库本身就是最好的备份。

**性能优势**：静态生成意味着内容在构建时就已经转换好了，访问时不需要查询数据库，直接返回 HTML。这让页面加载速度极快。

唯一的缺点是无法提供原生的评论功能和实时搜索，但可以集成第三方服务来解决（比如 [Giscus](https://giscus.app) 评论系统、[Algolia](https://www.algolia.com) 搜索）。不是什么都要自己做，知道什么时候该借助外部服务也很重要。

### 为什么不用复杂的内容管理系统（CMS）

市面上有很多功能强大的内容管理系统，比如 [WordPress](https://wordpress.org)、[Ghost](https://ghost.org)、[Strapi](https://strapi.io) 等，但我选择了最简单的方案——直接用文件系统。

我希望写作的过程是简单的、自然的。打开编辑器，写下想法，保存，提交到 Git。不需要登录后台，不需要填写表单，不需要点击各种按钮。所有内容都是 [Markdown](https://www.markdownguide.org) 文件，可以用任何编辑器打开，可以用 [Git](https://git-scm.com) 追踪每一次修改。

这样的写作体验最接近于在纸上写字——简单、直接、纯粹。作为开发者，我深知复杂系统的维护成本。能用简单方案解决的问题，就不要引入复杂度。而且，这种方式还有个额外的好处：内容完全属于自己，不会被任何平台锁定。

## 得与失

任何选择都有代价。自建博客带来了自由和掌控，但也意味着放弃了一些东西。

### 失去的

**社区和流量**：离开 xLog 和其他内容平台，意味着失去了平台自带的读者群体。不会有推荐算法把文章推给感兴趣的人，不会有平台内的互动和讨论。流量需要自己去积累，这是一个缓慢的过程。

**即开即用的功能**：没有现成的评论系统、搜索功能、统计分析。需要的功能都要自己实现或集成第三方服务。遇到技术问题需要自己解决，没有客服可以求助。

**维护成本**：虽然现在的架构很简单，但仍然需要关注依赖更新、安全补丁、性能优化。技术栈更新时可能需要做适配。这些都需要时间投入。

**平台功能的缺失**：没有现成的内容推荐、用户关系链、站内消息等社交功能。这些功能在内容平台上是标配，但在自建博客上需要付出很大代价才能实现，而且价值有限。

### 得到的

**完全的掌控权**：可以实现任何想要的功能，不受平台限制。想加个新板块？写个功能就行。想调整样式？改改 [CSS](https://developer.mozilla.org/docs/Web/CSS) 就好。这种自由度是任何平台都无法提供的。

**内容的永久性**：所有内容都存在自己的仓库里，用 [Git](https://git-scm.com) 管理。平台会关闭，服务会终止，但这些文本文件会一直存在。十年后回头看，它们还在那里，格式依然可读。

**技术实践的机会**：从架构设计到细节实现，整个过程都是学习和成长。尝试新技术、解决实际问题、在性能和体验之间找平衡点——这些实践经验能帮助我更好地理解系统设计的本质。

**真正属于自己的空间**：这不只是一个博客，而是一个可以随心所欲打造的数字空间。可以为重要的人创建专属板块，可以用粉色营造温馨氛围，可以把想法和回忆都保存在这里。这种归属感，是托管在别人平台上永远无法获得的。

**性能和体验的极致**：没有平台的限制和历史包袱，可以用最新的技术实现最好的体验。从渲染策略的选择、到色彩系统的设计、再到细节的打磨，每个环节都可以根据实际场景做针对性优化。静态生成带来极快的加载速度，精心调整的排版让阅读更舒适，[OKLCH 色彩空间](https://oklch.com)让设计更精确。这些细节在第三方平台上很难实现。

值得吗？对我来说，是的。失去的东西大多可以用其他方式弥补——流量可以慢慢积累，功能可以逐步完善。但得到的东西——掌控权、永久性、归属感——这些是无法从其他地方获得的。

选择自建不是因为它更好，而是因为它更适合我现在的需求。每个人的情况不同，权衡的结果也会不同。重要的是清楚自己真正想要什么，然后为此做出选择并承担相应的代价。

## 写在最后

从 [xLog](https://xlog.app) 迁移到自建博客，对我来说不仅是技术上的尝试，更是一次完整的实践。在这个博客的设计中，我发现技术不应该仅仅服务于技术本身。好的设计应该服务于目的，而不是为了技术而技术。

最让我满意的是「Mio 说」页面的设计。每次打开，看到标题和线条上那温暖的粉色点缀，会感觉到这个空间的氛围——温馨、独立、专属。这个颜色的选择不是随意的，而是经过深思熟虑的设计决策。

技术是工具，但用技术打造的空间可以很温暖。代码可以被复制，但设计背后的思考和用心，却是独一无二的。如果你也在考虑自建博客，不妨想想：你想通过这个空间表达什么？你想要什么样的氛围？技术选型应该服务于这些目标。

技术不是最重要的，重要的是你想通过技术实现什么。但掌握技术，能让你更自由地表达。
