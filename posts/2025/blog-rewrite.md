## 为什么离开 xLog

在过去的几年里，我一直在 xLog 上写博客。xLog 是一个基于区块链的去中心化博客平台，它的理念很好，但随着时间的推移，我发现它逐渐不再适合我了。

首先，**xLog 已经停止开发**。作为一个开发者，我深知一个不再维护的平台意味着什么——没有新功能，没有 bug 修复，没有性能优化。更重要的是，随着 Web 技术的快速发展，一个不再迭代的平台会逐渐落后于时代。

其次，**平台上充斥着低质量内容**。去中心化的理念固然美好，但缺乏内容审核机制也意味着平台上的内容质量参差不齐。我希望我的博客是一个纯粹的技术分享和生活记录的空间，而不是被各种营销号和低质量内容包围。

最后，也是最重要的一点——**我需要更加定制化的内容**。在 2024 年，我和 Mio 发展了恋爱关系，我们希望有一个共同的空间来记录生活的点滴。xLog 的功能相对固定，无法满足我们个性化的需求。比如，我想要一个「碎碎念」功能来记录每天的小想法，想要一个「Mio 说」板块来专门记录 Mio 的发言（我无权编辑，只有她自己能更新）。

## 为什么选择自己开发

在决定离开 xLog 之后，我面临两个选择：使用现成的博客平台（如 WordPress、Ghost），或者自己从零开发。经过一番权衡，我最终选择了自己开发。原因有以下几点：

### 技术栈的成熟

**Next.js 16** 的发布让我看到了现代 Web 开发的新高度。App Router、React Server Components、混合渲染（静态生成 + 动态 API）——这些特性让构建一个高性能的博客变得前所未有的简单。

**React 19** 带来的 Server Components 和 React Compiler 让我可以在不牺牲性能的前提下，写出更简洁、更易维护的代码。不再需要手动优化 `useMemo` 和 `useCallback`，编译器会自动帮我处理。

**Tailwind CSS v4** 的 CSS-first 配置理念让样式管理变得更加直观。不再需要 `tailwind.config.ts`，所有配置都在 CSS 文件中完成。配合 OKLCH 色彩空间，我可以轻松实现一个现代化的主题系统。

### AI 编程的成熟

2024 年是 AI 辅助编程爆发的一年。有了 Claude、GitHub Copilot 等工具，很多重复性的代码工作都可以交给 AI 来完成。这大大降低了开发一个博客的时间成本。

比如，这篇文章就是我和 Claude Code 一起完成的——我提供想法和方向，Claude 帮我分析项目结构、整理技术细节，然后一起生成文章内容。整个过程非常高效。

### 成本的降低

得益于 Vercel 的免费托管服务，我不需要为服务器付费。配合 Next.js 的静态生成，整个博客的运行成本几乎为零。唯一的成本是域名费用，一年也就几十块钱。

### 全面的掌控

最重要的是，**我拥有对博客的完全掌控权**。我可以随时添加新功能、修改样式、优化性能，而不需要受限于平台的限制。所有的代码都在我的 GitHub 仓库中，我可以随时查看、修改、备份。

当然，自己开发也有劣势。最大的问题是**需要投入时间和精力**。从项目搭建、功能开发、样式设计到部署上线，每一步都需要自己动手。但对我来说，这个过程本身就是一种学习和成长，是值得投入的。

## 设计理念

在开发这个博客的过程中，我遵循了以下几个设计原则：

### 极简主义

我希望这个博客的设计是**极简的**。没有花哨的动画，没有复杂的交互，只有纯粹的文字和内容。整个网站只使用黑、白、灰三种颜色，配合简洁的排版，让读者的注意力集中在内容本身。

在样式设计上，我采用了 OKLCH 色彩空间。相比传统的 RGB 或 HSL，OKLCH 在感知上更加均匀，能够提供更好的颜色一致性。比如，亮色模式和暗色模式的颜色过渡更加平滑，不会出现某些颜色过亮或过暗的问题。

```css
/* 亮色模式 */
--color-bg-primary: oklch(1 0 0); /* 纯白 */
--color-text-primary: oklch(0.15 0 0); /* 深灰 */

/* 暗色模式 */
--color-bg-primary: oklch(0.15 0 0); /* 深黑 */
--color-text-primary: oklch(0.98 0 0); /* 亮白 */
```

### 阅读体验优先

作为一个博客，**阅读体验是第一位的**。我在排版上做了很多优化：

- **最佳阅读宽度**：文章内容区域限制在 65-70 个字符宽度，这是经过科学研究的最佳阅读宽度
- **行高和字间距**：使用合适的行高（1.6-1.8）和字间距，让文字呼吸
- **系统字体优先**：使用系统默认字体（`system-ui`），加载速度快，渲染效果好
- **代码字体优化**：为代码块选择了多个流行的编程字体作为 fallback
- **平滑滚动**：为页面添加了平滑滚动效果，提升导航体验

### 性能至上

在性能优化上，我采用了以下策略：

#### 混合渲染

博客使用 Next.js 的混合渲染模式：

- **文章页面**：静态生成（SSG），构建时预渲染所有文章
- **文章列表**：静态生成，构建时生成文章索引
- **OG 图片**：动态生成（API Route），实时渲染社交分享图片
- **RSS 订阅**：动态生成，保证内容始终是最新的

这种混合模式既保证了页面的加载速度，又保留了动态功能的灵活性。

#### React 编译器

启用 React 19 的编译器（`reactCompiler: true`），自动优化组件渲染：

```typescript
// next.config.ts
const nextConfig: NextConfig = {
  reactCompiler: true, // 启用 React 编译器
  reactStrictMode: true,
}
```

编译器会自动插入 memoization，减少不必要的重新渲染，提升运行时性能。

#### 细节优化

- **字体加载优化**：使用 `font-display: optional` 避免布局抖动
- **图片优化**：所有图片都经过压缩和优化
- **预连接**：对外部资源（如 Google Fonts）使用 `preconnect` 和 `dns-prefetch`
- **平滑主题切换**：使用内联脚本在页面加载前设置主题，避免闪烁

```html
<script>
  ;(function () {
    const savedTheme = localStorage.getItem('theme')
    const systemTheme = window.matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light'
    const theme = savedTheme || systemTheme
    document.documentElement.classList.add(theme)
  })()
</script>
```

### 语义化和可访问性

作为一个现代化的网站，**语义化和可访问性**是必须要考虑的：

- **语义化 HTML**：使用正确的 HTML 标签（`<article>`、`<nav>`、`<header>`、`<footer>`）
- **ARIA 标签**：为交互元素添加合适的 ARIA 属性
- **键盘导航**：所有功能都可以通过键盘访问
- **跳转到主内容**：为屏幕阅读器用户提供「跳转到主要内容」链接
- **Focus 样式**：为所有可聚焦元素提供清晰的 focus 样式

```tsx
<a
  href="#main-content"
  className="sr-only focus:not-sr-only focus:absolute focus:top-4 focus:left-4"
>
  跳转到主要内容
</a>
```

### SEO 友好

作为一个技术博客，**SEO** 也是非常重要的：

- **结构化数据**：为每篇文章添加 BlogPosting Schema
- **Open Graph**：自动生成 OG 图片，优化社交媒体分享
- **Sitemap 和 Robots**：自动生成站点地图和 robots.txt
- **RSS 订阅**：提供 RSS 2.0 格式的订阅源
- **语义化 URL**：文章 URL 使用文件名作为 slug，简洁易读

## 技术架构

### 文件组织

整个项目采用了清晰的文件结构：

```
blog/
├── app/                    # Next.js App Router
│   ├── [slug]/page.tsx     # 文章详情页
│   ├── posts/page.tsx      # 文章列表
│   ├── thoughts/page.tsx   # 碎碎念
│   ├── mio-says/page.tsx   # Mio 说
│   ├── timeline/page.tsx   # 大事记
│   ├── about/page.tsx      # 关于
│   ├── api/og/route.tsx    # OG 图片生成
│   └── rss/route.ts        # RSS 订阅
├── components/             # React 组件（kebab-case）
├── lib/                    # 工具函数和配置
├── posts/                  # 文章内容（按年份组织）
└── data/                   # 数据文件
```

所有的配置和工具函数都集中在 `lib/` 目录下，便于管理和维护。

### 内容管理

文章采用 Markdown 格式，使用 Front Matter 存储元数据：

```markdown
---
title: 博客重构记
date: 2025-11-24
excerpt: 记录从 xLog 迁移到自建博客的心路历程
---

文章内容...
```

这种方式简单直接，不需要数据库，所有内容都是纯文本文件，方便版本管理和备份。

### 动态功能

除了静态的文章页面，博客还包含一些动态功能：

- **碎碎念**：记录每天的小想法，支持小时级别更新
- **Mio 说**：Mio 的专属发言空间，只有她能编辑
- **大事记**：展示重要的时刻和里程碑
- **旧文章提示**：自动检测文章发布时间，超过 365 天显示提示横幅

这些功能的数据都存储在 `lib/` 目录下的 TypeScript 文件中，通过代码即可管理。

## 设计权衡

在开发过程中，我也做了一些权衡和取舍：

### 不使用数据库

最初我考虑过使用数据库（如 PostgreSQL 或 MongoDB）来存储文章和评论。但最终我决定**不使用数据库**，原因有：

1. **简单性**：Markdown 文件 + Git 版本管理已经足够简单和可靠
2. **可移植性**：所有内容都是纯文本，随时可以迁移到其他平台
3. **成本**：不需要为数据库服务付费
4. **备份**：Git 自动提供了版本历史和备份

唯一的缺点是无法提供评论功能，但我可以通过第三方评论系统（如 Giscus）来解决。

### 不使用 MDX

虽然 Next.js 支持 MDX（Markdown + JSX），但我选择了**纯 Markdown**：

1. **简洁性**：Markdown 语法简单，适合纯文本编辑
2. **兼容性**：Markdown 是标准格式，任何编辑器都支持
3. **性能**：纯 Markdown 不需要在客户端执行 JavaScript

如果未来需要在文章中嵌入复杂的交互组件，我可以再考虑迁移到 MDX。

### 不使用 CMS

市面上有很多优秀的 Headless CMS（如 Contentful、Strapi），但我选择了**文件系统**：

1. **掌控感**：所有内容都在我的代码仓库中
2. **离线编辑**：可以在任何地方使用任何编辑器写作
3. **版本管理**：Git 提供了完整的变更历史

缺点是没有图形化的管理界面，但对我来说，Markdown 编辑器 + Git 已经足够了。

## 总结

从 xLog 迁移到自建博客，对我来说是一次全新的尝试。这个过程让我更深入地理解了现代 Web 开发的技术栈，也让我对自己的博客有了更强的掌控感。

虽然自己开发需要投入时间和精力，但这个过程本身就是一种学习和成长。而且，有了 Next.js、React、Tailwind CSS 这些优秀的工具，开发一个现代化的博客已经不再是一件困难的事情。
